# Working in this repository

This repository is the xds template: a single set of design tokens, component libraries for eight clients (four of them for the web), a sample app for each client, and the `xds` CLI that scaffolds a new project with a chosen subset of clients. `acme` is the placeholder name replaced by `xds create`, so keep it in all package names, identifiers, and file paths.

## Where things are

| Path | Contents |
| --- | --- |
| `design/tokens` | Design tokens in DTCG format (the single source of truth) |
| `design/themes` | Color themes, each defining an accent ramp and a neutral ramp |
| `design/components.json` | Component contract: variants, sizes, tones, and the source file for each client |
| `tools/design-build` | Token compiler and WCAG contrast checker |
| `packages/ui`, `packages/ui-solid`, `packages/ui-vue`, `packages/ui-svelte`, `packages/ui-native`, `crates/acme-ui`, `kotlin/ui`, `flutter/ui` | Component libraries for the web (React, Solid, Vue, and Svelte), React Native, GPUI, Compose, and Flutter |
| `apps/desktop-electron`, `apps/desktop-tauri` | Desktop shells that run the selected web app and its design preview |
| `packages/ui-core` | What the web libraries share: the prop types, class recipes, and stylesheet of their components, the DOM helpers their behavior needs, the web design preview as data (`src/preview`), and the behavior tests that each of them runs. It imports no framework |
| `apps/*`, `kotlin/*App`, `flutter/app` | Client apps, each with a design preview screen |
| `cli`, `template.json` | The `xds` CLI and the manifest mapping repository paths to client targets |
| `npm` | The npm packages of a release: the CLI's launchers, the build and consumer check of the web library (`npm/web`) and of the React Native library (`npm/react-native`), and their publication (`npm/publish.ts`) |
| `maven` | The Compose library of a release: its build into a Maven repository, its consumer check on the desktop and Android, and its upload to Maven Central (`maven/upload.ts`) |
| `crates-io` | The GPUI library's crates: their packaging for crates.io and their consumer check on macOS |

## Rules

- Design tokens are the source of truth. Never edit generated files (`packages/tokens/src/generated`, `crates/acme-tokens/src/generated.rs`, `kotlin/ui/src/commonMain/kotlin/acme/tokens/Tokens.kt`, `flutter/ui/lib/src/tokens/tokens.g.dart`). Edit the JSON files in `design/tokens`, run `mise run tokens`, and commit both the token sources and the generated files.
- Components must take all colors, sizes, and spacing from tokens. Do not hardcode hex colors in components, and prefer tokens over raw pixel values. Component-specific colors belong in that component's group in both `color.light.json` and `color.dark.json`.
- Every foreground and background color pair rendered together by a component must have an entry in `tools/design-build/src/contrast.ts`. The token build fails if any pairing falls below its required contrast ratio.
- Every component, variant, size, and tone must exist across all clients under the same name and appear in each client's design preview. TopBar, TabBar, and BottomSheet are touch-only exceptions and exist only on React Native, Compose and Flutter. Tooltip and Sidebar are pointer-only exceptions and exist only on the web targets (React, Solid, Vue, and Svelte) and GPUI. Update `design/components.json` in the same change. A difference between clients that is not in the contract's names (an option only some clients have, a part the platform draws, a different presentation for touch) is listed in that component's `differences`.
- The Electron and Tauri shells reuse the app selected by each shell’s `web` script. Changes to a shared component belong in its web library. Keep the `/` and `/design` routes working inside each shell.
- The web apps share one design preview, written once as typed data in `packages/ui-core/src/preview` and drawn by each web library's renderer (`src/preview.tsx`, `src/preview.ts` in Vue, or the `src/preview` directory in Svelte, on the library's `./preview` subpath). Add a web component to the preview there, not in an app: put its props in `components.ts`, show it in `sections.ts`, and add it to the `COMPONENTS` of each renderer, which fails to typecheck until it is there and takes every prop the data passes. Its `README.md` says how a renderer works.
- On the web, the libraries share `packages/ui-core` and must look and behave the same. A component in any of them takes its classes and its CSS from `packages/ui-core`; the overlays and the composite controls take their behavior from Zag.js, and the selection controls and fields are native inputs. Change a component's look or a behavior that does not depend on the framework in `packages/ui-core`, then check every web library against it in both color modes. `packages/ui-core` keeps one copy of what the web libraries share, including the DOM helpers their behavior needs, so it never imports a framework, and its CSS selects on its own part classes, native pseudo-classes, `aria-*` attributes, and Zag's state attributes.
- Every web component puts its root part class (`rootPart()`, `acme-<name>`), the app's class (`className` in React) and the app's style on its root element, and part classes start with `acme-`: the published library renames them `xds-`, and its stylesheet styles only elements with such a class and what they hold. A component with a variant, size, tone, shape, ratio or layout reads its default from the closest `Defaults` (`DEFAULT_OPTIONS` in `packages/ui-core/src/defaults.ts`), and a component drawn inside another passes every such option explicitly, so an app's defaults never change a component's own parts. The shared checks for both are in `packages/ui-core/test`.
- The web library's npm packages are built from the same sources by `npm/web/build.ts`, which fails if `acme` is left in them. `mise run check:library-web` installs them in new apps outside the repository and compares their design previews with scaffolded apps pixel by pixel; CI runs it on every change, and the release publishes them only when it passes. See `docs/web-library.md`.
- In Compose, a component takes every token from the theme in effect, never from a constant: colors and sizes from `LocalColors` and `LocalSizes`, and the shared values through the group properties of `acme.tokens` (`Space.s4`, `Typography.body`), which read `LocalTheme`. Read them in composition and hand the values to drawing and layout lambdas, which cannot read the composition. A component with a variant, size, tone, shape, ratio or layout takes its default from `LocalComponentDefaults` (`Defaults.kt`), and a component drawn inside another passes every such option explicitly. `DefaultsContractTest` holds the options to `design/components.json`.
- In GPUI, a component takes every token from the theme registered with the app, never from a constant: `theme(cx)` for the shared values and sizes (`t.space.s4`, `t.pointer.control_md`) and `palette(cx)` for the colors of the mode in effect, read where the component draws and handed to what it builds. A component with a variant, size, tone, shape, ratio or layout takes its default from `defaults(cx)` (`defaults.rs`) when the app gives none, and a component drawn inside another passes every such option explicitly. Every component implements `Styled` and puts the app's style on its root element, or on its surface for an overlay, after its own; an option that would share a name with a `Styled` method is named for the component (`control_size`, `icon_size`). The test in `defaults.rs` holds the options to `design/components.json`.
- In React Native, a component takes every token from the theme in effect, never from a constant: `useColors()`, `useControl()` and `useTheme()`, and a style sheet built with `themed()`, once per theme. A component with a variant, size, tone, shape, ratio or layout takes its default from `useDefaults()` (`defaults.ts`), and a component drawn inside another passes every such option explicitly; its own text is `PartText`, which takes nothing from `Defaults`. Every component puts the app's `style` on its root view, or on its surface for an overlay.
- The React Native library's npm package is built from `packages/ui-native` and `packages/tokens` by `npm/react-native/build.ts`, which fails if `acme` is left in it. Its Expo modules are optional peers, loaded inside a `try`, and its support window is the peer range in `build.ts`. `mise run check:library-react-native` installs it in an Expo app and in apps on the oldest and newest supported React Native, type-checks and bundles them, and compares their design previews on an Android emulator pixel by pixel; CI runs it on every change up to the bundles, and the release publishes it only when it passes whole. See `docs/react-native-library.md`.
- The GPUI library is the `xds-tokens` and `xds-ui` crates of a project that `xds create` makes under the name `xds`, packaged by `crates-io/build.ts`, which fails if `acme` is left in them, or if `xds-ui` does not ask for exactly the GPUI Kit that `Cargo.toml` pins and `docs/gpui-library.md` names: GPUI keeps no compatibility between releases, so a GPUI upgrade changes all three together. `mise run check:library-gpui` consumes the crates from a new crate outside the repository and compares its design preview with a scaffolded project's pixel by pixel, drawn off screen on macOS by `crates/acme-ui/examples/render_preview.rs`; CI runs it on every change, and the release builds and checks the crates without publishing them yet. See `docs/gpui-library.md`.
- The Compose library is the `ui` module of a project that `xds create` makes under the name `xds`, built by `maven/build.ts`, which fails if `acme` is left in it. Its public API may expose Compose's types and kotlinx-datetime's, which are `api` dependencies, and no other library's. `mise run check:library-compose` consumes it from new desktop and Android apps outside the repository and compares their design previews with a scaffolded project's pixel by pixel; CI runs it on every change on the desktop, and the release publishes it only when it passes on the desktop, on Android and for iOS. See `docs/compose-library.md`.
- `.github/workflows/release.yml` publishes only for a tag. Run by hand (`gh workflow run release.yml`), it rehearses the release: every job runs, each step that creates or publishes something runs only for a tag (`if: github.event_name == 'push'`), and a step beside it (`!= 'push'`) rehearses it with the same script and `--dry-run`. Give a new publishing step its rehearsal, which must fail when a secret the step needs is missing or refused. See "Rehearsing a release" in `docs/cli.md`.
- Do not edit theme color ramps by hand. `design/themes/indigo.json` is the reference theme; generate new themes with `node tools/design-build/src/make-theme.ts <name> --hue <0-360>`.
- Every top-level path in the repository must be accounted for in `template.json` (under a target, a shared group, `common`, or `exclude`). Target-specific lines in shared files must be wrapped in `@if <names>` and `@endif` comments. A name is a target id or a shared unit from `template.json`; use the unit (`@if js-workspace`) when the lines serve every target that requires it, so that a new target gets them too. Use `@if template` for lines needed only in this template repository.
- Machine-written JSON files under `design/` must be formatted with `JSON.stringify(value, null, 2)` followed by a trailing newline.
- Write comments that explain why, not what.
- Fix what the linter reports. Where a rule is wrong for one deliberate line, disable it there with `// oxlint-disable-next-line <plugin>/<rule> -- <why>`; a directive that no longer suppresses anything fails `mise run check:js`.
- On the command line, type checking (each package's `typecheck` script, `tsrs --noEmit`) and oxlint's type-aware rules (`tsrs-lint`) run on tsrs, an experimental Rust port of TypeScript 7.1. Editors keep TypeScript's own language server; the root `typescript` package is the version to point them at, and the one tsrs is held to. tsrs is built from one TypeScript commit, so the pnpm catalog pins both exactly and they move together: to upgrade TypeScript, change both, taking the tsrs release that ports the new version (`pnpm view tsrs@<release> tsrs.typescriptVersion` shows the version a release ports). `mise run check:js` fails while they differ. Build scripts do not type-check; `check:js` does it once, before the web builds. The Vue packages are the exception: `.vue` files need vue-tsc (`vue-tsc --noEmit`), which runs on the TypeScript 6 API that typescript-native-bridge keeps over the TypeScript 7 checker; those packages take that `typescript` from the `vue` catalog, and Vite's compiler for `.vue` files needs it too.
- The Svelte packages (`packages/ui-svelte`, `apps/web-svelte`) type-check with svelte-check instead, whose `--tsgo-experimental-api` checks them with TypeScript 7, found as `@typescript/native` at the catalog's `typescript` version. svelte-check still reads `.svelte` files with TypeScript 6's JavaScript API, so `.pnpmfile.cjs` gives it a TypeScript 6 of its own; delete the hook and the alias once svelte-check runs on TypeScript 7 alone. Upgrade svelte-check together with TypeScript. oxlint lints the script of a `.svelte` file, but not with its type-aware rules, and leaves unused names there to svelte-check (`noUnusedLocals`).
- Rust code follows the lints in `[workspace.lints]` of `Cargo.toml`, which `mise run check:rust`, `check:desktop` and `check:cli` deny. They are how the pinned toolchain's idioms reach the code, whoever writes it: Clippy proposes an API once `rust-version` reaches the release that stabilized it (`map_or_default`, `is_none_or`), so `rust-version` stays at the release `mise.toml` pins. Fix what Clippy reports, with `cargo clippy --fix` where it offers one, and by hand where its fix does not compile. Where a lint is wrong for one deliberate item, write `#[expect(clippy::<lint>, reason = "<why>")]` there, never `#[allow]`; a lint that is wrong for all of this code is allowed in `Cargo.toml`, with the reason above it. Do not turn on `clippy::suboptimal_flops`: its `mul_add` rounds the contrast calculation differently.
- Rust written from memory is older than the toolchain. Prefer what the pinned release has, including the idioms no lint proposes: let chains (`if let Some(a) = x && a > 0`), `if let` guards on match arms, `let ... else`, `assert_matches!` (`use std::assert_matches;`), `std::sync::LazyLock`, `Option::is_none_or`, `map_or_default` on `Option` and `Result`, `bool::ok_or`, `Vec::pop_if`, `Vec::push_mut`, `<[T]>::array_windows`, `<[T]>::as_array`, `str::strip_circumfix`, `std::fmt::from_fn`, `cfg_select!`, `Path::is_empty`, and `bit_width` on the integers. Each of these compiles on the pinned toolchain; before using anything newer, compile it there, because release notes have listed APIs a release does not have.
- Add a native package to the Expo app with `pnpm exec expo install <package>` in `apps/mobile`, not `pnpm add`, so that it gets the version the Expo SDK expects. See "Moving to the next Expo SDK" below.

## Checking a UI change

Flutter compares widget goldens on Linux. Inspect the design preview in both light and dark modes on every client you modify. On the web, `mise run compare:previews` starts every web app and compares their previews with each other pixel by pixel: every section and every `?open=` overlay, at 1280 and 390 px, in both modes. A difference is a library drawing a component differently, since every app draws the same data. It is not part of `mise run check`.

How the interactive web components behave (keyboard, focus, and ARIA state) is tested in the Google Chrome installed on the machine, with the same checks for every web library. The checks are in `packages/ui-core/test`: `behavior.ts` finds elements by role and name and depends on no framework, and `scenarios.ts` writes the screen each check runs against as data, in the form of the design preview's. Each library's test file (`test/behavior.test.tsx` in `packages/ui` for React and `packages/ui-solid` for Solid, `test/behavior.test.ts` in `packages/ui-vue` for Vue and `packages/ui-svelte` for Svelte) draws those screens with the library's preview renderer and runs the checks. When you add or change an interactive web component, add its scenario and its checks to `packages/ui-core/test`; the libraries' test files do not change.

## Changing the CLI

`cargo test --package xds` scaffolds a test project for every individual client and every combination of clients. The test suite fails if any repository file is not mapped in `template.json`, if any conditional comment marker is unbalanced, or if an unreplaced placeholder remains in a generated project. Files under `cli/overlay` are copied over the root of generated projects using the same conditional markers and placeholder renaming.

## Moving to the next Rust release

The toolchain is pinned in `mise.toml`, and `rust-version` in `Cargo.toml` names the same release, which is what lets Clippy propose that release's APIs.

1. Change the version in `mise.toml` and in the example in `docs/cli.md`, run `mise install`, which updates `mise.lock`, and set `rust-version` in `Cargo.toml` to the new minor release.
2. Run `cargo clippy --workspace --all-targets --fix`, then `cargo fmt --all`, and fix by hand what is left. A fix that does not compile is reverted for its whole crate, which hides the others: pass `-- -A clippy::<lint>` to leave that lint out, and fix its places by hand.
3. Compare the lints of the two releases (`clippy-driver -W help` under each toolchain) and read each new lint outside the default groups. Take one in `[workspace.lints]` when it is right for this code; a lint that argues with GPUI's conventions (a closure in a builder chain, `&mut Window` and `&mut App` in every signature, a builder that returns `Self`) stays off.
4. Add what the release stabilized to the idioms in "Rules", and only after compiling each on the new toolchain. The release notes of 1.100.0 list `bool::toggle`, `Vec::from_fn` and the never type, and 1.100.0 has none of them.
5. Run `mise run check:rust`, `mise run check:desktop`, `mise run check:cli` and `mise run //desktop-tauri:check`.

## Moving to the next Expo SDK

The Expo app stays on the versions its SDK expects: `mise run //mobile:check` fails when an installed native package differs from the list in the installed `expo` package. It reads only that list, offline, so it does not fail when Expo publishes a newer patch; moving to one is a change of its own.

1. Wait until the `expo` release is a day old (pnpm's minimum release age) and, for a new SDK, until `https://api.expo.dev/v2/versions/latest` lists Expo Go for it: `mise run //mobile:ios` runs the app in Expo Go.
2. In `apps/mobile`, run `pnpm add expo@~<sdk>.0.<patch>`, then `pnpm exec expo install --fix`, which moves every native package to the SDK's version. It leaves `typescript` alone: `expo.install.exclude` in `apps/mobile/package.json` keeps the catalog's version, which moves with tsrs.
3. Give `packages/ui-native` the app's new versions in its peer and dev dependencies.
4. Compare the versions of `react` and `react-dom` the SDK pins with the catalog's in `pnpm-workspace.yaml`, which the web targets share. If they cannot take the SDK's React, give the two mobile packages a named catalog of their own (`catalogs.native`, under `@if mobile-react-native`) rather than versions of their own.
5. Read the breaking changes of the SDK and of its React Native release, then run `mise run check:js` and open the design preview in Expo Go on iOS and Android, in both color modes.
